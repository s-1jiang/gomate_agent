# 同城游玩行程

对话中的游玩安排、半日游和一日游进入行程流程；单纯“查咖啡馆地址”仍走地点查询。现在支持一到三天、整个方案最多六个停留时段，同城步行、公共交通或驾车。同地可安排休息，跨日可重访。骑行、跨城、天气与实际预约尚未接入。

可直接输入：“明天9点从杭州东站出发，17点前返回，两个人，想轻松逛西湖并吃午餐，安排每一站怎么玩。”

## 处理过程

1. Supervisor 结合当前会话提取日期时段、出发点、人数、预算、交通方式和要求，分派 activity / dining / places 研究候选。
2. 地点通过第一轮审查后，确认出发点，并由对应研究角色调用可选 Tavily 查询玩法与实用资料。
3. Supervisor 将候选、原始需求、来源和固定时间窗口交给 itinerary Agent。专家选择顺序、用餐休息、每站建议停留时长和具体玩法。
4. 程序调用高德路径规划2.0，按逐段交通耗时向上取整到分钟，加入明确展示的缓冲，计算到达、离开、返程和剩余时间。检查日期覆盖、重复/未知地点、来源归属、截止时间和明确的站间步行上限。
5. 时间或来源冲突会由 Supervisor 退回行程 Agent；语义审查也可要求其定向修改。每次携带版本、反馈和旧方案，最多额外两轮，保留原 Run 的预算/截止时间。仍有冲突不发布方案，不用假的交通时间兜底。

## 路线失败处理

- 公共交通某段明确无路线时，查询同一对地点的真实步行路线。默认只接受单段不超过 2000 米，用户指定的总步行上限继续约束整份方案；明确不接受步行时不尝试。驾车或纯步行不会自动换成别的出行方式。
- 步行衔接采用高德返回的耗时、距离、指引和轨迹，重新计算到达、停留、返程及截止时间，仍需 Supervisor 审查。页面按每段实际方式显示，摘要可显示“公共交通 + 步行”。
- 步行过远或两种方式都无路线时，将路段、出发时间和原因交回行程 Agent，调整顺序或替换非必去地点；不能放宽用户时间、必去地点、返程和步行约束。最多沿用原两轮返工，仍不可行才向用户指出具体路段并询问调整。
- 同一个 Run 内复用成功路线与明确无路线结果。公交缓存区分出发日期和分钟；步行及驾车按地点对缓存，不跨用户或跨 Run 复用。
- 超时、连接失败或服务暂时不可用，最多额外查询一次；所有尝试共享原预算、取消状态与截止时间。权限、配额和格式错误不会触发步行替代或无效返工；错误码保留在后台 Run 和脱敏日志，页面显示简短的服务重试提示。

`TRANSIT_WALK_FALLBACK_METERS=2000` 控制公交无路线时的单段步行上限，范围 0—5000 米，设为 0 可关闭。更新 `.env` 后重新创建 backend 和 worker；无需额外密钥。

前端从同一个结构化 `map_result.itinerary` 渲染时间轴、交通、每站玩法、来源和待确认事项。在第一站与后续行程之间嵌入位置示意及按需交互地图。无底图时仍展示供应商坐标；仅绘制实际返回的轨迹片段，缺失路段不连直线。历史消息持久保存相同方案，旧版地点消息继续可读。

日期未知时默认明天，时段未知时采用一日9—18点/半日13—18点；假设保留在内部请求中，页面直接展示实际日期和交通安排。出发点未知则每天从首站开始计时，页面标为“开始游玩”；要求返程却未给出发点、地点重名、路线不可用或关键条件矛盾时追问。跨午夜时间包含明确日期与 `+08:00`，显示时区固定为 Asia/Shanghai。

出发点名称允许带地图已知的城市全称或去掉“市”的前缀，例如“大连星海广场沙滩”匹配“星海广场沙滩”。这只处理精确名称与城市前缀，不做模糊猜测；多个同名候选仍需确认。

## 来源和未核实信息

- `[M#]`：高德 POI，包括名称、地址、坐标、ID 和查询时间。
- `[T#]`：高德已查询的站间路线、交通估计、距离、换乘提示和查询时间。公交带规划出发日期/时间；驾车时间为查询时的估计，不保证未来路况。
- `[W#]`：Tavily 返回的网页链接、标题、原文片段、查询时间和对应 POI。只发送公开城市/地点研究词，不发送会话、出发住址、私有 RAG 或用户身份。原文作为数据处理，不作为指令。
- `[R#]`：原有私有资料召回，保持用户与会话隔离。

页面保留来源标签、原文链接和片段，隐藏 POI ID、坐标系、查询过程及审查记录。玩法统一标为建议；具体开放/预约信息需有该地点的网页来源，否则只保留一次出发前提醒。网页检索不是现场营业核验。未计算完整费用，不声称满足预算；园内步行、排队、停车与未来交通变化尚未完整计算。后台时间校验与 Supervisor 审查保持不变。

## Tavily 配置

从 [Tavily 控制台](https://app.tavily.com/) 获取 Key，在本机 `.env` 添加：

```dotenv
TAVILY_API_KEY=your-key
WEB_SEARCH_TIMEOUT_SECONDS=12
CHAT_MAX_OUTPUT_TOKENS=4096
DEEPSEEK_THINKING=disabled
```

然后运行 `docker compose up -d --force-recreate --wait`，让 API 和执行任务的 Worker 都读取新配置，并刷新前端代理。首次更新代码使用 `docker compose up -d --build --wait`。

Compose 将密钥传给后端，前端不接收 Tavily Key。适配器固定请求 `https://api.tavily.com/search`，basic 模式、每个候选最多三条、关闭生成答案与原始网页抓取。未配置、无结果、鉴权或限流失败时继续生成建议，不向用户展示密钥或配置诊断；可选检索失败的错误码记录在后端日志。预算/取消/Run 超时不能因此被绕过。

高德查询沿用 `AMAP_WEB_SERVICE_KEY`；交互底图仍需 `AMAP_JS_API_KEY` 和仅在服务端使用的 `AMAP_JS_SECURITY_CODE`。
同一进程的地点/路线请求默认至少相隔1.1秒，避免并行研究和连续算路造成突发请求；可按实际高德账户配额调整 `AMAP_MIN_INTERVAL_SECONDS`。等待仍受原 Run 截止时间控制。

默认显式关闭 DeepSeek 思考模式，避免多阶段结构化调用使用服务端默认高思考而超时；可用 `DEEPSEEK_THINKING=enabled` 自行启用并相应调整时限。空回答与字段结构不匹配合计最多补一次校正，共用原调用预算，不对网络、鉴权、拒答或超长失败隐式重试。[DeepSeek 思考模式参数](https://api-docs.deepseek.com/guides/thinking_mode/)

## 验证与范围

`python -m scripts.smoke_itinerary` 使用临时 SQLite、假密钥和模拟 HTTP，验证完整时间表、往返交通、联网来源、Supervisor 返工、预算、持久化和幂等，不调用外网。测试还覆盖超时窗、伪造地点/来源、过期审查、重名出发点、路线失败和搜索降级。

`python -m scripts.smoke_transit_fallback_live --live` 显式调用真实高德，以公开的“大连星海广场 → 星海广场沙滩”核对公交无结果时的步行路线和时间表，不调用模型或访问数据库。该样例固定公开 POI ID 以排除同名地点；供应商数据变化时可能需要更新样例。

2026-11-24 真实公开样例已通过：杭州东站09:00出发，断桥、午餐、湖滨公园、苏堤，16:48返回东站，17:00截止，余量12分钟。该次使用真实 DeepSeek/高德和临时数据库，未使用已有用户数据；未配置 Tavily，所以玩法仍是建议。单个样例通过不保证未来交通或任意需求均可行。

真实 Tavily 鉴权与浏览器交互 SDK 仍待配置联调，不由模拟测试证明。尚未具备完整预算求解、营业窗口验证、固定地点的确定性锁定、酒店间跨日转场和跨城规划。

官方接口依据：[高德路径规划2.0](https://lbs.amap.com/api/webservice/guide/api/newroute)、[Tavily Search](https://docs.tavily.com/documentation/api-reference/endpoint/search)。
